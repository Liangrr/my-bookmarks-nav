# 星轨 bookmark-nav-site · 项目结构

> 一个 git 仓库装三块代码：**Web（Next.js，在仓库根）**、**小程序（Taro，在 `apps/mini/`）**、**两端共享的数据与纯逻辑（`packages/`）**。
> 本文件只回答「哪里放什么、谁读谁」；结构决策的取舍理由与踩坑记录见 [开发规范.md](./开发规范.md) §3.26。
> 最后核对：2026-10-18（体积为当日实测值，会随数据增长变化）。

## 一、总体布局

```
bookmark-nav-site/
├── src/                            Web（Next.js 16 + React 19）——仍在仓库根，Vercel Root Directory 不变
│   ├── app/                        路由、页面、API、全局样式与站点元信息
│   ├── components/                 页面级 UI 组件（多数是 "use client"）
│   ├── lib/                        Supabase 客户端与表单校验工具
│   ├── data/                       未抽入共享包的残留数据（见 §3.5）
│   └── middleware.ts               /admin 服务端路由守卫
├── public/                         静态资源（不经构建处理的图片）
├── apps/mini/                      小程序（Taro 4.3 + React 18 + webpack5 + TS）
│   ├── src/                        页面源码（pages=主包 / subpackages=分包）
│   ├── config/                     Taro 构建配置，含共享包别名与编译白名单
│   ├── types/                      全局类型声明
│   └── package.json / package-lock.json / node_modules/   小程序独立依赖
├── packages/                       两端共享（唯一真源）
│   ├── shared-data/src/            12 个数据 JSON + 法定节假日表
│   └── shared-lib/src/             3 个无运行时依赖的纯逻辑模块
├── tests/                          vitest 单测（挂在根 npm 下）
├── scripts/                        数据校验、抓取与链接体检脚本
├── docs/                           本文件与开发规范
└── .github/workflows/deploy.yml    CI：校验通过后再部署 Vercel
```

## 二、三层职责与数据流

| 层 | 路径 | 职责 | 由谁构建 |
|---|---|---|---|
| Web | 仓库根（`src/` + 根配置） | SSR / SEO、API 代理、路由级鉴权、页面渲染 | Vercel（CI 自动部署） |
| 小程序 | `apps/mini/` | 微信端页面 | 本地手跑 `npm run build:weapp`（**未进 CI**） |
| 共享 | `packages/` | 数据与纯逻辑，单一真源 | 不单独构建发行，两端按源码编译 |

**数据流**：改数据只动 `packages/shared-data/src` 一处 → Web 与小程序同时生效，不存在两份副本。

**共享包怎么被解析**：
- Web 侧 = 根 [tsconfig.json](../tsconfig.json) 的 `paths`：`@shared-data/*` → `./packages/shared-data/src/*`、`@shared-lib/*` → `./packages/shared-lib/src/*`。Next 当一方源码编译，不需要 `transpilePackages`。
- 小程序侧 = [apps/mini/config/index.ts](../apps/mini/config/index.ts) 的同名 `alias`，外加 `mini.compile.include` 把两个目录加入编译白名单（Taro 默认不编译 `node_modules` 外的 TS 源码，所以 alias 指向真实路径而非软链）。
- 边界隔离：根 tsconfig `exclude: ["apps"]`，避免 Web 的 React 19 类型与小程序 React 18 类型互相污染；两端 `tsc` 各自跑。
- 单元测试与数据校验也走同一套别名（见 [vitest.config.ts](../vitest.config.ts)）。

### 3.2 API 路由

| 路由 | 作用 |
|---|---|
| `api/bookmarks/[id]/click/route.ts` | 书签点击计数（限流） |

### 3.5 `src/data/`（为什么还在）

| 文件 | 为什么没抽进共享包 |
|---|---|
| `chrome-bookmarks.json` | 个人浏览器书签导出，代码里无任何引用——属于隐私项，不宜进共享包，也待处理 |
| `zhuiju.ts` | 只被 `scripts/` 下的 Python 链接检查脚本读取，Web / 小程序都不用 |

这两个文件**不参与数据体检**（体检只扫 `packages/shared-data/src` 的 12 个文件）。

## 四、小程序 `apps/mini/`

| 路径 | 作用 |
|---|---|
| [src/app.config.ts](../apps/mini/src/app.config.ts) | 主包 / 分包划分 + 窗口样式。**`pages` 只放轻页，带大 JSON 的页面一律进 `subPackages`** |
| `src/pages/index/` | 主包：首页菜单聚合墙（`index.tsx` + `index.config.ts` 页面级配置） |
| `src/pages/profile/` `src/pages/todos/` `src/pages/login/` `src/pages/todo-edit/` | 主包轻页：个人页、待办列表、登录、待办新建 / 编辑。待办不直连 Supabase（weapp 无 fetch），统一走 Web 端 `/api/auth/*` 与 `/api/todos`，token 存 Taro storage |
| `src/lib/api.ts` / `src/lib/todo-format.ts` | 小程序端请求封装（带 401 自动刷新）与待办时间格式化 |
| `src/subpackages/budget/` | 分包页面：三餐预算。Taro 分包路径 = `root` + `pages`，所以跳转必须写 `/subpackages/budget/index` |
| `src/app.ts` / `src/app.css` | Taro 应用入口与全局样式 |
| [config/index.ts](../apps/mini/config/index.ts) | 别名（`@shared-data` / `@shared-lib` / `@`）+ `mini.compile.include` + pxtransform / cssModules 开关 |
| `config/dev.ts` / `config/prod.ts` | 开发 / 生产两份 Taro 配置 |
| `babel.config.js` | `babel-preset-taro`；其 `@babel/preset-react` 是 peerDependency，**必须显式装进 devDependencies** |
| `project.config.json` | 微信开发者工具的项目配置（appid、编译设置等） |
| `tsconfig.json` / `types/global.d.ts` | 小程序端的 TS 配置与全局类型声明 |
| `dist/` | 构建产物（已 gitignore，可直接按目录核算主包体积） |

**体积约束**：主包上限 **2MB**，单个分包上限**同样 2MB**。2026-10-28 实测主包 **351K**（首页 / 个人 / 待办三件套）、分包 560K（三餐预算）；分包前主包是 952K。

| `diy-guide.json` | 44K | Web `/diy` |

### 5.2 `shared-lib/src`（纯逻辑，无 DOM / React 依赖）

| 文件 | 导出 | 谁用 |
|---|---|---|
| `index.ts` | 汇总 re-export（`export * from` 四个模块） | 两端 |
| `meal-budget.ts` | `cheapest` / `priciest` / `fitBudget` / `shouldSuggestSaving` / `computeSavingPlan` | Web `/meals`、小程序分包预算页 |
| `feast-filter.ts` | `filterFeastPlaces`（聚餐门店的地区 / 菜系 / 关键词筛选） | Web `/meals` |
| `todos.ts` | `groupTodos` / `isOverdue` / `summarize` / `validateTodo` + `Todo` 等类型（东八区自然日/自然周口径） | Web `/todos`、小程序待办页 |
| `convert-sheet.ts` | `pickSheetInput` 等 | Web `/convert` |

四个模块都有对应 vitest 单测（见 `tests/`），改逻辑必须同步改测试。

## 七、常用命令

Web（在仓库根）：

```bash
npm run dev              # 本地开发
npm run typecheck        # tsc --noEmit
npm run validate:data    # 数据体检
npm test                 # vitest
npm run lint             # eslint
npx next build --webpack # 本机必须带 --webpack（缺 Turbopack 原生绑定）
```

小程序（在 `apps/mini/`）：

```bash
npm run build:weapp      # 构建微信小程序，产物在 dist/
# 首次安装依赖后若报原生二进制缺失：
npm approve-scripts --all && npm rebuild --foreground-scripts
```

产物核算（主包 / 分包分开算）：

```bash
find apps/mini/dist -type f -not -path "apps/mini/dist/subpackages/*" | xargs du -k | awk '{s+=$1} END {print s"K"}'
find apps/mini/dist/subpackages -type f | xargs du -k | awk '{s+=$1} END {print s"K"}'
```

## 八、已知边界（当前不做的事）

1. **小程序构建未纳入 CI**：CI 只校验并部署 Web；小程序需手动 `build:weapp` 后交微信开发者工具上传。
2. **`living-guide.json`（1836K）上不了小程序**：单个分包上限也是 2MB，打包成 JS 后更大，必须外置到云存储 / 接口或拆章加载才可能接入。
3. **`meal-planner.json` 未拆分**：小程序分包 560K 里约九成是预算页完全用不到的 251 家聚餐门店（webpack 无法 tree-shake JSON）。拆成「个人套餐 + 聚餐门店」两份可让分包降到约 50K，但会同时牵动 Web 组件、体检脚本与 2 个单测，尚未实施。
4. **`src/data/` 的两个残留文件**：`chrome-bookmarks.json`（无引用、隐私项）、`zhuiju.ts`（仅 Python 脚本读）。
5. **小程序仅验证过构建**：未在真机 / 微信开发者工具里跑过，交互与样式尚待实测。
